## 1. `match_one` is not proof — what was additionally verified

`match_one` masks `jal`/HI16/LO16 and never links, so it is blind to a wrong
callee (§87), a duplicated/wrong jump destination (§81) and a mis-derived `%lo`
(§84). **This draft deliberately uses derived offsets, so §84 blindness was a live
risk.** `.run/giants/s21_g21_reloc_verify.py` closes all three: it RESOLVES every
relocation in the object (symbol address + the *implicit REL addend*, which
`objdump -r` does not print — that is the §84 trap in tool form) and compares it
against the address the target's disassembly names at the same instruction index.

```
checked: 359 jal callees, 406 %hi/%lo data addresses, 60 internal j targets
mismatches: 2      <- both are the switch table (see below)
```

* **359/359 `jal` callees resolve to the target's function addresses.**
* **60/60 internal `j` destinations resolve to the target's instruction indices** — §81's jump-table-duplication blindness closed *inside* the function.
* **406/406 `%hi`/`%lo` data addresses resolve correctly, including all 6 derived-offset sites.** Hand-check, independently: `0x8018E2DC-0x60 == 0x8018E27C`, `0x8018E2E8-0x60 == 0x8018E288`, `0x8018E2F4-0x60 == 0x8018E294`, `0x8018E27C+0x60 == 0x8018E2DC`, `0x8018E288+0x60 == 0x8018E2E8`, `0x8018E294+0x60 == 0x8018E2F4` — 6/6, and each `+0x30` partner likewise.
* The **only** unresolved relocation is the switch table: this object emits a local `.rodata` table where the target uses `jtbl_801F4CE4` (21 entries + a trailing `0`, verified against `asm/ov_SC07_006/data/tail11.data.s`). That is the 3-step `jr` carve chain, owned by banking.

**This tool is reusable and should be kept** — it is the missing rung between
`match_one` and the whole-binary gate for any `jr` function.

## 2. REFUTED: round 1's §83d diagnosis of the cases-0/3 CSE

Round 1 concluded the case-0/3 address CSE was gated by `cse.c:8340`'s
whole-function quantity budget (`max(nsets*2,500) + max_reg`), and that only a
function-global pseudo-count change could move it. **All three parts of that are
wrong**, and disproving it is what unlocked the function:

1. **A 15-line reproducer reproduces the CSE exactly** (`.run/giants/g21/r0.c`:
   two call groups sharing three symbols, separated by four calls). `max_reg`
   there is ~100, not ~1500. ⇒ not budget-gated. This also bought a **sub-second
   iteration loop** in place of the 40-second monster rebuild.
2. **Reading the code:** `max_qty` only gates whether `cse_basic_block` *extends
   into the next basic block* (`cse.c:8550`); exceeding it inside a block calls
   `abort()` (`make_new_qty`, `cse.c:810`), it does not silently change a
   decision. Both call groups are in **one** basic block — `cse_end_of_basic_block`
   ends a block only at a `CODE_LABEL`, and there is none between them (verified:
   the only branch targets in that span are idx 295/300/315, all *before* group 1;
   and `jtbl_801F4CE4` holds exactly the 21 case addresses, no hidden label).
3. **It is not a register-pressure/rematerialisation story either.** The target
   uses **only `$s0..$s6`**: `$s7` and `$fp` appear **zero** times in the whole
   5,122-instruction function. Two callee-saved registers sat free while the
   address constants were "rematerialised", so no allocation contest can explain it.

**Correct diagnosis:** CSE was active across that span in the target (it holds the
`const_int 1` in `$s0` across all seven call sites) but did **not** merge the
`symbol_ref`s. Identical source ⇒ identical RTL, so **the target's group-2 address
expressions must be structurally different rtx from group-1's.** Confirmed from a
second direction: **`C01` contains the same two groups over the same three symbols
and has ZERO residual** — because a `break` puts a `CODE_LABEL` between them and
flushes CSE's table. `C00`/`C03` have no such boundary.

**Cookbook-worthy generalisation:** *diagnose the SCOPE of a compiler decision by
shrinking it to a minimal reproducer before theorising about whole-function state.
If a 15-line function reproduces the symptom, no global explanation is admissible.*
(§83d as written is now a refuted entry and should be corrected in place.)

## 6. WHAT IS STILL OPEN — read this before banking

**Two of the seven levers are hand-placed dials, not recovered original source.**
The draft is byte-equal to the target either way, but the *source* is not the
author's, and that matters for the next person:

1. **L1 (§84 derived base).** The target's case-0/3 group-2 address expressions
   are structurally distinct rtx from group-1's; that is proven by elimination
   (§2). *Which* distinct spelling the author used is **unknown**. Constraints the
   real spelling must satisfy, all measured: it must give each of the three group-2
   addresses its **own** base symbol (rows 17/18), and the `+0x30` partner must
   still derive from it with a single `addiu` (so not a second absolute symbol).
   The data layout is a contiguous 8-record × 12-byte table at `0x8018E27C`
   (`D_8018E2A0`'s 60-byte blob covers records 4..7 — splat only made symbols at
   directly-referenced addresses), so the author very likely had *names* for
   records 4..7 that splat never created. **If those four symbols get named, the
   natural spelling probably falls out immediately.**
2. **L3 (KIND==1 compare constant).** Makes 4 of the 35 template instances differ
   in source from the other 31 — implausible for a block that is otherwise proven
   to be one copy-pasted definition. The compiler behaviour is real and
   K-dependent: for KIND≠1 the target materialises `li $v0,1` *inside* the loop
   (identical to a uniform-source build), and only for KIND==1 does it hoist a
   second `1` into `$s5`. Both uniform spellings were measured and neither
   reproduces the mixture (rows 21/22). Mechanism is `loop.c:1631`
   `(threshold * savings * m->lifetime) >= insn_count` with
   `threshold = (loop_has_call ? 1 : 2) * (1 + n_non_fixed_regs)`, and
   `combine_movables` (`loop.c:1259-1286`) summing `savings` across movables whose
   `set_src` are `rtx_equal_p` — i.e. a second `(const_int 1)` movable in the loop
   flips it. **Next probe:** find the uniform source shape that puts a second
   `const_int 1` in the KIND==1 loop body only — the obvious candidate is that
   `sp40[7] = s5` is *not* a variable store in the original but something that
   constant-folds per instance.

3. **Not whole-binary verified.** The build was not run (concurrent work owns the
   tree; `asm/` was in fact wiped mid-session and had to be waited out). Banking
   still needs the 3-step `jr` carve chain for `jtbl_801F4CE4`, and only the
   whole-binary SHA1 proves the derived offsets (§84's lesson: a `match_one` MATCH
   that fails the binary by ONE byte is a masked-field bug).

**THE SINGLE HIGHEST-VALUE NEXT MOVE:** run the carve chain + whole-binary gate.
If it goes green the function is banked as-is and the two dials become a *source
provenance* question, not a correctness one — worth logging but not blocking.
If it fails, diff the built overlay against the payload and read the differing
word first (§84 diagnostic), before touching the C.
