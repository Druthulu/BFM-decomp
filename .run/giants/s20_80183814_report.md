## 1. What is actually left — ONE fork, not 36 problems

I mapped every residual with a difflib opcode dump. All 36 fall into four classes and
**every class is a consequence of a single global register-allocation fork**:

**Class A — the address CSE (cases 0 and 3, ~30 ins).** At the end of case 0 the
source calls `func_8017D8A4(D_801BFCBC + off, &D_8018E27C, &D_8018E27C + 0x30, s3, 1)`
three times. Those same three symbols were already used ~15 instructions earlier in
the *same basic block* (the four `0x1000` calls on `D_801BFCB4`). gcc CSEs the six
address values and keeps them live across the calls:

```
MINE   move  $a1, $s3          TARGET   lui   $a1, %hi(D_8018E27C)
       move  $a2, $s6                   addiu $a1, $a1, %lo(D_8018E27C)
                                        addiu $a2, $a1, 0x30
```

That costs **2 extra callee-saved registers** (`$s7`, `$fp`), which pushes every real
variable one register along — `a0` lands in `$s7` instead of `$s2` — and that renaming
is what produces the 1201 register-sensitive mismatches.

**Class B — morph-loop giv copies (cases 6, 9, 11) — SOLVED late in the session.**
The target emits `addu $t1,$a2,$zero` / `addu $a3,$a1,$zero` before each lerp loop. I
first read this as pure allocation; it is not. The source walks **copies** of the two
input pointers and leaves the originals alone:

```c
mn = mp[4];
pa = msa; pb = msb;                /* <-- the two giv-init copies */
while (mn != 0) {
    md[0] = pb[0] + (((pa[0] - pb[0]) * f) >> 12);
    ...
    pa += 4; pb += 4; md += 4; mn--;
}
```

Note `md` is walked directly — copying it too (a third walker) over-adds. This took
cases 6 and 11 from 8 and 7 structural diffs to **0**, and case 9 from 5 to **1**.
This is the shape a copy-pasted source block would have, and it is worth a cookbook
entry: *when the target initialises a loop pointer with a redundant-looking `addu
Rx,Ry,$zero`, the source is walking a copy, not the original.*

**Class C — KIND==1 template instances (cases 13, 14, 17, 18; 12 ins).** The target
hoists `addiu $s5,$zero,0x1` (the kind) out of the loop and reuses it as the `p[1] == 1`
comparison operand (`bne $v0,$s5`). Mine emits a separate `li $v0,1` inside. This is
automatic constant-CSE that mine loses for the same allocation reason (for every
KIND != 1 instance, mine hoists correctly and case 20 is a **perfect 525/525**).

**Class D — case 19, 1 ins.** `mem - 0x8B - (rand() & 0x3F)`: target computes
`(mem - 0x8B) - r`, mine computes `mem - (r + 0x8B)`. Same instruction count, different
placement. Cosmetic; not worth a lever until A is fixed.

## 2. Why the CSE is a whole-function effect (read the compiler)

From `tools/reference/gcc-2.7.2/cse.c:8340-8356`:

```c
max_qty = val.nsets * 2;
if (max_qty < 500) max_qty = 500;
max_qty += max_reg;
...
if (val.nsets * 2 + next_qty > max_qty) break;   /* stop extending into next block */
```

The CSE quantity budget depends on `max_reg` — the **total pseudo count of the whole
function**. So whether CSE still holds `&D_8018E27C` when it reaches case 0's third
`func_8017D8A4` group is not a local property of case 0; it is gated by how many
quantities the earlier 4,700 instructions consumed. This is why the residual did not
respond to any local rewrite of case 0 (§80: the result is scoped to the base).

The corollary that matters: gcc's `reload` **rematerialises** an address constant whose
pseudo failed to get a hard register. The target's compilation had no spare callee-saved
register, so all six CSE pseudos were rematerialised. Mine has exactly 2 spare, so 2
survive. **Getting the pseudo count within a hair of the target's is the whole game.**

## 5. THE SINGLE HIGHEST-VALUE NEXT MOVE

**Kill the cases-0/3 address CSE. It is now the only thing left that matters.**

With the morph solved, 17 of 21 case bodies are structurally exact and the residual is
just: case 0/3 address CSE (18), the KIND==1 constant hoist (12), prologue/epilogue (4),
case 9 (1), case 19 (1). The CSE is upstream of almost all of it — it is what takes the
2 extra callee-saved registers, which renames every register in the function.

Concretely, in priority order:

1. **Find the ~5 spurious instructions** that put me at 5127 instead of 5122, using
   `s20_g14_g14_score.py` plus a difflib-opcode dump (the recipe is in §1). Length parity
   is worth buying on its own: it makes `match_one`'s number legible again, AND it
   perturbs `max_reg` — the exact knob in `cse_main`'s quantity budget (§2) that decides
   whether the case-0/3 CSE fires. These are the same lever.
2. **Re-run rows 7–14** of the do-not-re-buy table on the new base (d8). Three of the
   last behemoth's seven winning levers were negatives that inverted once the base moved,
   and row 6b just proved the same thing here — a "pure allocation" verdict I had already
   written down turned out to be a source-shape win.
3. **KIND==1 template instances (cases 13, 14, 17, 18).** The target hoists
   `addiu $s5,$zero,0x1` out of the loop and reuses it for the `p[1] == 1` compare.
   Cheap to probe: try spelling the compare against a variable that already holds the
   kind, or reordering `s5 = KIND;` relative to the `func_8012EC04` call.
4. Only then attack the CSE head-on. If it still survives, the remaining option is to
   accept it as a *reload* artifact and hunt for the ~2-pseudo difference that leaves the
   target with no spare callee-saved register.

Do **not** reach for register pins. Row 15 shows a pin halves the residual, which
proves the diagnosis, but it does not fix the frame and it is not source a human would
have written. (Row 15 was measured on d6; per §80 it should be re-measured on d8 before
being trusted as a diagnostic again.) The frame is 8 bytes over purely because of the 2 extra saved registers;
close the allocation fork and the frame closes with it.
