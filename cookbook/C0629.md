# Tell which pool a view's object lives in without tracing spawns

Context: 3.45 T17 judges c2-c4 (wave A1, 143 player/render-hinted types; the layout hint was wrong for ~30 of them).
- Overlay header map: `hdr->f5C` is the small-object handler table, `f60` the actor table, `f64` the fx table
  (src/shared/ov/func_80144B9C.h:237-239). Each table is indexed by the slot's +0x0 u16 type (pool walker
  src/shared/ov/func_8017849C.h:15-35), so a function reached from entry N of a table owns kind N of that pool.
- The overlay header also writes the player: player+0x1E8 / +0x1F0 hold table pointers (func_80144B9C.h:115, 235-236);
  player state handlers run from `D_8017FE70[D_80126BA4](&guess_g_PlayerActor)` (ov_MAIN_012_jr_801458E0.c:1421, all 133
  overlays); script callbacks sit at player+0x1F8 (func_8016EE94.h:29-41).
- Render records: `func_80146578` allocates sprite slots, `func_8014659C` model slots; the fx spawner `func_8012913C`
  puts a sprite at fx +0x20. Sprite vs model: a u8 write at +0x24..+0x27 is the sprite (the model keeps an s32 TMD list
  at +0x24); any access past +0x38, or an inline MATRIX at +0x34, is the model (GsCOORDINATE2 at +0x30).
- A 0x68 pool exists too (POOL68, D_8011F9D0, 20 records; freed with a 0x68 clear; md_MAIN_046.c:702-716).
- Traps: callers cast actor slots to the player type (cls_1662435c3ee1.h:3) and POOL68 records to the player type
  (md_MAIN_046.c:696): judge by the code, never the cast. CAST_ALIAS(s32, (u32 *)b, k) puts the field at byte 4k.
