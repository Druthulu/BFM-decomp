# Find the real parent by its pool, not by the placeholder's address name

Context: 3.45 T16 judges (c1-c4). `Unkstruct_800B5CB8`, the anchor of the 241-type actor family, was named after
`D_800B5CB8`, which is sprite record #4 (`guess_g_RenderWork` 0x800AF630 + 0x65A8 + 4*0x38), not an actor. Its definition
(a P37 max-site split) merged three objects that one helper set touched: the 0x10C actor slot, the 0x38 sprite record
and the 0x84 model record. Widths clash at +0x10/+0x18 (u16 sprite vs s32 actor velocity) and +0x24.

Technique:
1. Subtract the placeholder's address from the known pool bases (config/symbols.<bin>.txt: guess_g_ObjectTable,
   guess_g_RenderWork, guess_g_SmallObjectPool, D_8011DB30 ...) to see which record it really names.
2. Find each pool by its allocator: a scan with a fixed stride and a free test (`*(u16 *)slot == 0`), e.g.
   guess_SpawnActor src/shared/ov/func_8012C658.h:8-48 (0x10C x 96), guess_AllocSpriteObject src/800.c:8820-8828 (0x38).
3. The pool walker gives the type field: src/shared/ov/func_8017849C.h:15-35 calls `D_8011DB08[*(u16 *)slot](slot)`:
   +0x0 u16 is the object type (handler index into the overlay header's table), +0x2 the per-type state.
4. A view's parent = the pool its pointer comes from (caller arg, +0x64 parent link, +0x20 render pointer); its
   variant = the owning handler `overlay:func`.
5. Split a merged placeholder per source by the pool each source reaches, never by the widest layout.

Pools found (T16): actor 0x801202A0 96x0x10C; sprite 0x800B5BD8 256x0x38; model 0x800AF8D8 192x0x84 (GsCOORDINATE2 +0x30);
fx 0x8011DB30 128x0x38; small objects 0x8011D030 30x0x58; player 0x80126B58 (0x254, ZeroMemory func_80145CEC__05c7cfc4.h:51).
Trap: casts.tsv's `off` is the macro index, not bytes, under `CAST_ALIAS(s32, (u16 *)b, k)` (byte = k * sizeof(u16)).
