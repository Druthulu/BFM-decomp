# C0547 — Return retype void->int on a decl is not always byte-neutral (dropped result still moves regalloc)
tags: declarations,return-type,lying,bytes,regalloc · date: 2026-11-07 · phase/task: 3.41/T4 · origin: P3.41 T4.c1

# Retyping a decl's return void→int: neutral for 181 of 182 callees, not for all

- 3.41 T4.c1: 182 callees, 75,801 `extern` decl lines rewritten so that the return type matches the def. The rewritten lines were `void`→def type, or def `void` with no caller using the value. Gate result: 218/218 with one callee dropped.
- func_80139BE0 (decl void→s32; the call `func_80139BE0(obj);` drops the result) still moved bytes in func_801376E8 (`src/shared/ov/func_801376E8.h`, every `*_jr_80135D20.o`, 129 binaries). In the objdump, `move v0,s1` moves earlier and a0/a1/v0/v1 are allocated differently. A call through a non-void prototype marks `$v0` as set even when the result is dropped, and that changes the register allocation.
- Rule: a mass return retype gates on the full fleet, never on argument alone. Bisect a failing batch with an object-by-object compare of a HEAD build against the edited build (`.run/P41/T4/objcmp.py` pattern), then revert the culprit callee fleet-wide as one unit.
- A non-extern prototype inside a body TU conflicts with a rewritten `extern`; fix it in place in the same unit.
- Related: C0543 (unit rule), C0103/§92 (pointer changes are caller-neutral, width changes are not).
