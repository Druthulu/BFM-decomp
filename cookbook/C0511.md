# C0511 — Type-census instrument pitfalls: attrs in layout hash, tag+typedef one name, intra-canon liveness, stale ledger rows
tags: census,structs,types,gate,ledger · date: 2026-09-30 · phase/task: 38/T7 · origin: P38 T2-T6 summaries

## Type-census instrument pitfalls: what made "one definition per type" read wrong (P38 T2-T6)

A struct-unification census is a gate; each of these moved its counts by tens to thousands:
- **Layout hash must include alignment attrs** (`__attribute__((packed))`, `aligned(N)`). Two definitions that
  differ only in attrs are different types; hashing members alone merges them and a fold breaks bytes. Layout-hash
  equality is not type equality anyway: member-type twins, same-name members at other offsets (silent to cc1).
- **A definition's struct tag and its typedef are ONE name** (`typedef struct X {…} X;`). Counting the two C
  namespaces apart doubles names and invents dup classes; but a tag and a typedef of the same name with DIFFERENT
  layouts are two types (split them `N_tag`/`N_td`).
- **Dead-name liveness must count uses inside the canonical headers** (intra-canon fixpoint). A metric that skips
  them flags every member-only type dead, and deleting those breaks the build.
- **Stale ledger rows**: a judge that writes a row only for units it draws keeps a unit's old KEPT verdict after a
  hand edit fixes the source; a census reading the ledger then over-counts (18 "conflicting types" rows, all stale).
  Read latest-verdict-per-unit through the judge's own function and re-check the source before trusting a residue.
- **Include graph must model the compiler's search order** (relative, then each `-I`); ignoring `-I` reports types
  in `include/` as "not visible".
- **A control that compares against a doc may be a hard-coded list**, not a parse; fixing the doc alone does not move it.
- Gate on a phase-scoped reading (`--check-structs`), not the global `--check` whose other terms belong to later phases.
