# A two-sided ratchet for a long consolidation: fail above and below

Context: 3.45 T8 `struct_twins.py --gate` (config/consolidation_ratchet.tsv); a multi-task cleanup (pending types, casts by form,
pending ledger rows) that must only move down, wave by wave.

- One committed row per metric `metric count task note`; the gate FAILs when a count is above its row (regression) and also
  when below ("ratchet stale: lower it"). The second side is the point: a slack ratchet lets a re-added cast or a new pending
  row pass silently, and it forces each batch to commit its lowered counts in the batch's own commit.
- `--write-ratchet` rewrites from the current tree and refuses to raise an existing row; a `--final` mode requires every count 0.
- Counts must be deterministic (sorted, fixed tie-breaks; two runs cmp-identical, C0582) or the two-sided test flaps.
- A ratchet input owned by another file (here the DECL-PARAM rows of config/lying_exceptions.tsv) moves it too: write the ratchet
  last, from the HEAD that holds every input (T8.c2 rewrote it after T8.c1 committed 26 rows).
- Prove it bites in a scratch worktree (C0601): one planted regression per metric kind, then the revert passes.
