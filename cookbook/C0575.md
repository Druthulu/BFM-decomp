# C0575 — git grep with many -e patterns stalls; join into one -e per chunk (rename_scan hang)
tags: grep,performance,rename_scan,git,hang · date: 2026-11-11 · phase/task: 3.43/T9 · origin: T9.c4

# git grep with several -e patterns is orders of magnitude slower than one joined pattern

**Trap (3.43 T9.c4).** `git grep -E -e P1 -e P2 ...` (git 2.43) falls back to per-line matching per pattern; one
`-e` is searched over the whole buffer. rename_scan --spec built one `-e` per rename form: 96 patterns for B1's 48
renames over 20,382 files (669 MB) ran 11.5 CPU-hours without output.

**Measured.** 1 rename as 2 `-e`: 26.4 s; each form alone 0.7-1.8 s; 5 renames (10 `-e`) > 60 s. Same alternation
joined into ONE `-e P1|P2|...`: 1/5/10/25/48 renames 2.2/2.5/2.9/4.3/6.9 s, identical lines. `[aA]` classes, `\b`
and alternation are not the cause. `-P` does not escape it (96 `-e` > 100 s); `-F -i` with 81 tokens also > 100 s.
GNU grep -E with the two patterns on the same files: 0.37 s.

**Fix.** Join forms into one ERE per chunk (tools/rename_scan.py grep_chunks, 32 renames per chunk) and bound the
wall clock (GREP_WALL_S, exits non-zero). Old vs new on T8 batch2/batch4: byte-identical -v output, 351 s -> 13.5 s,
684 s -> 13.5 s. Same shape remains in run_ledger's `git grep -o -w -F` (fast today). Related: C0570 (git grep -f).
