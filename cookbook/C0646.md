# Render pointee by access offsets; a zero-arg C call still passes a0

Context: P3.45 T17.c33 (read-only judge on c31's residual Unkstruct_800B5CB8 sources, snapshot 5fdda71562).

- A render pointee (actor/fx +0x20, holder +0xCC/+0xD0/+0x6C) is a sprite (Unkstruct_800B5BD8, 0x38) or a model
  (Unkstruct_8001C9D0, 0x84). List each source's offset+width accesses through the cast:
  - any access >= 0x38 -> model (size exclusion, the accepted R7 rule); e.g. +0x48/+0x4C/+0x50 s32 = model unk48..unk50.
  - only +0x0..+0x13 -> `head-only`: the render head is laid out the same in both; no per-kind parent can be told
    (c33: 327 sources / 1,374 sites, incl. the generic damage path func_80131340 and func_8017AE2C's pv).
  - a width the other layout cannot hold at that offset (sprite u8 unk27 vs model s32 unk24) decides between the two
    only when the actor's own variants are excluded too (they also have u8 +0x24..+0x27 in extA).
  - accesses at +0xB0..+0x108 through a holder pointee -> not a render record at all.
- Folding a view to a new parent changes the access width wherever the old member was wider (800B5CB8 unk14/unk1C s32
  vs s16 in both candidates): check every key's offsets against the parent before the fold.
- `func_8017AE2C(pv)` looked unreached because its callers are spelled `f()` in C; in the asm a0 is the caller's own
  incoming a0, saved and restored around the jal (ov_*: func_801789AC 801789BC/801789CC; func_80178970 80178978).
  Follow the register in the retail asm up to the actor table (f60 roots, C0629), not the C argument list.
