# A per-file walk cache must not decide the merge order: rebuild results in input order

Symptom: a census over a per-file walk cache prints different counts on an unchanged tree (type_census `struct_map:` 14373/770 vs 14376/770; 14239/769 after touching 68 .c files).

Mechanism (tools/type_census.py walk_all, before 3.44 T2):
- `results = {}`; cache misses are walked and inserted first (`results[r["rel"]] = r`);
- then `for rel in files: results[rel] = r` fills hits; re-assigning an existing key keeps its old dict position, so misses stay ahead of hits.
- `results.values()` order thus depends on which files' mtime changed. Any order-sensitive consumer (a union-find with vetoed merges, first-wins setdefault, most_common ties) changes output.
- Second, quieter split: cached entries are JSON round-tripped (tuples -> lists, int keys -> str), fresh ones are not.

Fix:
- build a separate `fresh` dict, then `results = {rel: fresh.get(rel) or cache[key] for rel in files}` (sorted input order);
- have the pool worker return `json.dumps(walk)` and `json.loads` it in the parent, so fresh == cached in type. Keep the dict-returning worker for other callers (restruct.py calls `tc._walk_worker`).
- a generated doc compared byte-for-byte prints no wall-clock stamp (C0562).

Proof: cold, warm and partial-touch -j 8 runs print the same line and the same doc sha; the old code on the partial-touch run differs.

Same pattern still in tools/lever_census.py:864-875 (at 3.44 T2).
