## Rationale
- Order: baselines and the frozen worklist (T1), because rank43 renumbers on every run. Tooling fixes before any real rename (T2): today a rename leaves the old name's ledger row dead and copies spec values unchecked (R3.43-002). The deferred items that edit bodies and walls (T3 for I4, T4 for I3) before naming, so batches comment final bodies. Citations of the 1,083 existing names (T5) before new names, so the citation gate is on for every later batch. Evidence and dossiers (T6) before naming. A reviewed pilot (T7) before the fleet. Data (T8) before functions (T9-T11): a function that reads a named datum names more easily (data before processing). The ledger-to-comment pass (T12) after the names, so it can check every guess pointer, and after T4's re-tags. Record (T13). The Ghidra mirror (T14) right before the gate, so the developer's live Ghidra keeps running until then. Gate (T15), close docs (T16), cleanup (T17).
- The frozen worklist: "the top 500 of 3.42's ranking" is the 500 rows with rank43 <= 500 in docs/leverage.tsv as committed at e328006dab (unchanged to HEAD). Its check (every row disposed of, names present in each member's symbol stack and the ledger) lives in the 3.42 scanner (T2), as the milestone asks.
- Cited versus guess: a name is cited only on evidence the project observed and recorded with a pointer: a string at its address, the debug menu, live RAM verified per R10, an xref chain from a cited anchor, the EXE header, or a library symbol if the developer adds that kind. A community address recorded as reported (G5) backs a `guess_` only. A model's reading of the code is code inference, so a `guess_` (rule 1: propose, never assert).
- One name per share class (rename_sym `class:<id>`; members in one binary get new, new_2, ...), never one per address; share headers are address keys and are never renamed (3.42 T3 binding). A multi-address class's name describes its body, not each address's role.
- Header comments go where the body is: the shared header for a class, every private copy for a ledgered family (575 families stay as they are, DECIDED), the .c for a single instance. Data have no canonical declaration (R3.43-001), so a datum's basis lives in names.tsv (and docs/memory-map.md for outside evidence), and T12 puts its ledger pointer on its declarations.
- docs/leverage.tsv: rename_sym's textual rewrite keeps names consistent at tiny diffs per batch; one regeneration at the gate (after a fresh type census) makes the file exact (`--check`). Regenerating per batch would renumber rank43 across most of a 19 MB file each time and grow the repository for nothing (the 3.42 close item: rerun leverage_rank after the renames).
- func_80037004 stays unnamed in 3.43 (rank43 24,186): config/rename_known.tsv and the wiki's Names-and-renames example stay valid as the 3.42 control (the other 3.42 close item). If a task names it after all, that task rewrites the wiki example in a dated past tense and retires the fixture.
- No live-RAM play session: tools/ram_probe.py needs someone playing scenarios in PCSX-Redux. Verified datapoints already in docs/memory-map.md count; reported addresses stay `guess_` names marked with their source. Claude can offer the developer a session later; nothing in the milestone needs one.
- Sequential batches, one in-house coder at a time: every batch edits the same symbol files, names.tsv and overlay .c files, and a parallel wave needs the developer's word (standing constraint).
- Gates per batch: the scanner (R32) is the rename's proof; R22 is the bytes' proof (names do not change bytes, except where a linker orders symbols by name: Risks).
- Effort: T7 is the one `effort: high` task: the naming conventions and the evidence bar that T8-T11 copy are judgments no test arbitrates; their mechanics (ledger, scanner, worklist check, gates) are tested.
- Struct types and fields keep their placeholders unless the developer chooses otherwise (Developer decides): they are not ranked units, and rename_sym cannot rename them (R3.43-002).
