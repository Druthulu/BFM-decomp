# T9.c4 — rename_scan grep hang: diagnose, fix; finish B1

## Cause
git grep (2.43) given several `-e` patterns appears to fall back to line-by-line matching per pattern, where one pattern is searched over the whole buffer; under `-E` (glibc regex) that is ~20x slower per extra pattern and grows with pattern count.
B1's scan passed 96 `-e` patterns (48 renames x strong+weak) over 20,382 tracked files / 669 MB, so it never finished; the same alternation joined into ONE `-e` runs in seconds.

- git grep -E, renames[:5], 10 -e: TIMEOUT at 60 s
- rename 0 forms alone, one -e each: old name 1.1 s; func_/D_ (6|7|8)-digit [aA] alternation 1.4 s; bare alternation 1.2 s; 0x form 1.5 s; bare [aA] 1.1 s; -i 1.1 s; -F -i 0.7 s; -P 0.7 s -> no single construct ([aA] classes, \b, alternations) is slow

- git grep -F -i, 2 tokens: 0.7 s; 81 tokens: TIMEOUT 100 s -> the fixed-string prefilter also suffers (multi -e)

## Fix (tools/rename_scan.py)
- grep_chunks(renames, size=GREP_CHUNK=32): pure; one ERE per chunk = every rename's strong/weak forms joined with `|` (same line set as the old -e list).
- grep_hits: one `git grep -n -I -E -e <chunk>` per chunk; overall wall-clock bound GREP_WALL_S=1800 via subprocess timeout -> sys.exit with a message (non-zero).
- _git(..., timeout=None) catches TimeoutExpired. classify/scan unchanged. Docstring line updated. Selftest: grep_chunks chunking + joined ERE matches the same fixture lines as the per-form patterns.
- Not done (out of scope): run_ledger's `git grep -o -I -w -F *pats` (line ~454) has the same multi -e shape; fast enough today, may slow as the ledger grows.
