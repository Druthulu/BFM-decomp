## Moves that cracked

- **func_8012EF34** (MATCH, score 0, 15 ins = target; 141/141 includers score 0;
  whole-object verdict IDENTICAL on every recipe): the pin was not a codegen
  artefact of the source but a *wrong prototype*.  The tree spells the shared
  header `void func_8012EF34(s32, s32)`, but 40+ call sites in `src/` declare it
  `extern s32 func_8012EF34(s32 a0, s32 a1);` and consume the return value
  (`if ((func_8012EF34(...) & ~0x1000) == 0)`), and `src/ov_SC01_084/
  ov_SC01_084_jr_80182A00.c` carries a WARNING (§181 law 2/4) that the `void`
  spelling "leaks" the return value the caller consumes.  Restoring the game's
  real `s32` prototype is the lever: the call's result stays live in $v0 across
  the `gte_stsz` asm, so local-alloc can no longer hand $v0 to the `&sp10` /
  reload temp and gives it $v1 ($3) instead — exactly the register the two
  `register ... __asm__("$3")` pins were forcing.  The body is lever-free: the
  call result is held in a plain `s32 r` and returned; no `register`, no
  `__asm__`, no launder, no barrier.
  ```c
  s32 func_8012EF34(s32 a0, s32 a1) {
      s32 sp10;
      s32 r;
      r = func_8012EFB8(a0);
      { s32 *p = &sp10; gte_stsz(p); }
      *(s16 *)(a1 + 4) = sp10;
      return r;
  }
  ```
- **func_8012EF70** (MATCH, score 0, 18 ins = target; 141/141 includers 0;
  whole-object verdict IDENTICAL): the same lever, one try.  `func_8012EF70` is

## Walls

- **func_800D02D0** (best 8 of 39 tries; wall tag `lreg-qty-order`): the target
  loads `D_800D3768[arg0].word0` into $v1 and keeps the `&D_800C7C60` pointer
  in $v0 (the pointer is also spilled to `16(sp)` as the 5th argument of
  `func_8001ABBC`).  A lever-free `p` makes the *load* take $v0 and the pointer
  $v1 — the mirror image of the target.  The cc1 dumps show why: with the
  `register s32 *p __asm__("$2")` pin, `p` is a hard register and the load is a
  separate local quantity; without it, `p` becomes a GLOBAL pseudo (it is live
  across the call to `func_8001ABBC`, 5 uses, dies in 2 places) and global-alloc
  gives it $3, while the block-local load keeps $2.  The target's assignment
  (`load` in $v1, `pointer` in $v0) is only reachable when the pointer is a hard
  register.  Tried and rejected: splitting `p` into two pointers (score 19 —
  the extra `lui/addiu` pair changes the length), the second address as a
  constant `&D_800C7C60` (best 8: the constant is materialised into $v0 but the
  load still takes $v0, and one `lui/addiu` pair is left over), the value
  through its own temp, the store through a `CdFileLoc *row` pointer, and the
  `D_800C7C64 = p` store spelled as `*D_800C7C64 = (s32)p` (score 24).

## Notes for the next reader

- The lever-free body of an item is `orig.c` minus the `register ... __asm__`
  lines; scoring it prints the residual against the target (a masked
  word-by-word diff with the register pairs), which is the fastest way to see
  what a candidate still has to fix.
- A header item is MATCH only if the score is 0 on EVERY includer: use
  `.run/P40/T10/tryinc.py <k> <header> <fn> <body>` for k = 0..n-1 (141
  includers here for the two overlay headers).
- The whole-object bank verdict is `tools/delever_oracle.judge_all` over the
  file's recipes (it writes the candidate into the real file and restores it);
  for a header that is 141 compiles, ~76 s.
- The two `s32` prototypes in `src/shared/ov/func_8012EF34.h` and
  `src/shared/ov/func_8012EF70.h` change what 141 includer TUs see.  The
  includers were all verified to still compile and to score 0, and the
  whole-object verdict is IDENTICAL on every recipe, so the tree's compiled
  bytes do not move.
- DECLARATION CENSUS (the one thing the expert must weigh): 1294 TUs declare
  `extern void func_8012EF34(s32, s32);` and 5 declare
  `extern s32 func_8012EF34(s32, s32);` (the 5 are the callers that consume
  the return value).  The shared header is the DEFINITION, so its prototype is
  what the 136 including TUs compile against; the 1294 `void` declarations are
  in TUs that do NOT include the header, so they only call it and never see the
  definition's type — a `void` declaration at a call site is compatible with an
  `s32` definition at link time (no name mangling in C), and the 1299 call
  sites' compiled bytes are unaffected because the callee's ABI is unchanged
  (the flag still leaves in $v0).  The 5 value-consuming sites were ALREADY
  declaring `s32` and reading $v0; the tree's own note in
  `src/ov_SC01_084/ov_SC01_084_jr_80182A00.c` says the `void` spelling
  "leaks" the return value and recommends reconciling to the s32 form.  If the
  expert prefers to keep the header's `void` spelling, this item is a WALL
  instead — but then the 5 value-consuming callers remain a known tree
  inconsistency, which is the status quo, not a regression.
- The `hd_*` cc1 dump directories were removed after use (the shard dir is
  1.5 MB).
